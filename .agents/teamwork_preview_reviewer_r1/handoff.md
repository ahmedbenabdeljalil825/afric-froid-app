## 1. What the Prior Attempt Got Wrong

### Issue 1: Fatal Preload Loading Failure in Electron BrowserWindow
- **Input:** Electron app launch (`npm run build:electron` or packaged `.exe`).
- **Expected:** BrowserWindow loads preload script and securely injects `window.electronUpdater`.
- **Actual:** `electron/main.ts` hardcoded `preload: path.join(__dirname, 'preload.js')`. Vite / `vite-plugin-electron` builds the preload script as `dist-electron/preload.mjs` (due to `"type": "module"`). `dist-electron/preload.js` did NOT exist on disk (`fs.existsSync` returned `false`). Electron BrowserWindow silently failed to load the preload script, resulting in `window.electronUpdater` being `undefined` in the renderer and breaking the entire Electron OTA updater mechanism.
- **Root Cause:** Hardcoded `.js` extension instead of checking for existing `.mjs` build artifact generated by Vite.

### Issue 2: Insecure Arbitrary IPC Exposure in `electron/preload.ts`
- **Input:** Context bridge execution in `electron/preload.ts`.
- **Expected:** Only dedicated, typed APIs (`window.electronUpdater`) exposed to renderer. No arbitrary IPC invocation.
- **Actual:** `electron/preload.ts` exposed `window.ipcRenderer` with raw, unconstrained `on`, `off`, `send`, and `invoke` for ANY channel.
- **Root Cause:** Copy-pasted boilerplate from generic Vite Electron templates. Violates Electron Security Guidance (CWE-200 / CWE-94) and Karpathy guidelines ("remove dead/orphaned code" since no application code uses `window.ipcRenderer`).

### Issue 3: Algorithmic Flaws in Semantic Version Comparison (SemVer 2.0.0)
- **Input:** 
  1. `compareVersions('1.5.1-beta.1', '1.5.1')`
  2. `compareVersions('1.5.0', '1.5.0-alpha')`
  3. `compareVersions('1.5.1+20260921', '1.5.1')`
- **Expected:**
  1. `-1` (Pre-release has lower precedence than standard release).
  2. `1` (Standard release has higher precedence than pre-release).
  3. `0` (Build metadata must be ignored in version precedence).
- **Actual:**
  1. `1` (Pre-release was incorrectly rated as *newer* than final release).
  2. `0` (Standard release was rated equal to alpha pre-release).
  3. Evaluated with build string included.
- **Root Cause:** Split on `.` without parsing pre-release (`-`) or build metadata (`+`), and `parseInt('1-beta', 10)` returned `1` with a phantom fourth index.

### Issue 4: False-Positive OTA Update Triggers on 404 / Network Errors
- **Input:** `androidOtaService.checkForUpdate()` when the GitHub repository has no published releases yet (HTTP 404), or when device is offline.
- **Expected:** Return `{ updateAvailable: false, ... }` and set status to `'not-available'` (or `'error'` for network failures) without opening prompts.
- **Actual:** The `catch` block caught HTTP 404 / errors and unconditionally manufactured a fake update `fallbackVersion = '1.5.1'` with `updateAvailable: true` and fired `setStatus('available')`. This caused `UpdatePrompt.tsx` to automatically pop up on every app startup in dev/browser/Android offering a nonexistent update.
- **Root Cause:** Developer conflated development simulation with production error handling by hardcoding fallback simulation in the general `catch` block.

### Issue 5: Missing Rate-Limit Throttling on Mobile Update Checks
- **Input:** Rapid successive invocations of `checkForUpdate()`.
- **Expected:** Throttled/cached check (e.g. 15-minute TTL) unless explicitly forced (`force: true`), plus graceful handling of HTTP 403 rate limits.
- **Actual:** Hit GitHub API on every check, risking 60 req/hr rate limit exhaustion on unauthenticated mobile networks.
- **Root Cause:** No timestamp caching or request throttling implemented in `androidOtaService.ts`.

### Issue 6: Test Suite Tampering / Disconnected Simulation Mocks
- **Input:** `node tests/verify-android-ota.mjs`.
- **Expected:** Imports and verifies the actual implementation in `services/androidOtaService.ts`.
- **Actual:** Test script defined duplicate local functions (`compareVersions` and local mock loops) and tested its own duplicates rather than the production service.
- **Root Cause:** Author avoided importing `.ts` files by creating duplicate mocks in the test runner.

### Issue 7: Countdown Timer Persistence After Modal Dismissal
- **Input:** User clicks "Dismiss" (X) or "Later" on downloaded Electron update prompt while 10-second countdown is active.
- **Expected:** Countdown timer cancelled.
- **Actual:** Countdown continued running in background and would trigger `handleApplyInstall()` even after modal was closed.
- **Root Cause:** Dismiss handlers in `UpdatePrompt.tsx` only set `setIsOpen(false)` without resetting `setCountdown(null)`.
